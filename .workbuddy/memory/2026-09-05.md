# 2026-09-05

## 歌词链路重构（Cassette / Navidrome）

用户反馈：Navidrome 服务器里已有歌词（.lrc 文件 / 内嵌标签），app 显示 "Lyrics not supported"。

### 根因
1. **能力门禁一票否决**（主因）。`LyricsService` 用 `capabilities.supports(.songLyrics)` 卡住请求，
   而 SwiftSonic 的 `fetchCapabilities()` 在 `getOpenSubsonicExtensions` 失败时**静默 catch**，
   扩展表变空字典并被 `loadCapabilities()` 永久缓存 → 一次网络抖动/反代拦截就永久禁用歌词。
   且 `supports` 实现是 `versions.contains(1)`，服务器只声明 v2 也会误判。
2. 只读 `structuredLyrics`，legacy `getLyrics(artist:title:)` 从未调用（SwiftSonic 已实现）。
3. 全项目无 LRC 解析器，纯文本歌词只能整块显示。
4. 语言码严格相等：`zh-CN`/`zho`/`cmn`/`eng` 匹配不上系统 `zh`/`en`。
5. 缓存无 TTL，`fetchedAt` 字段存在但从未用于失效判断。

### 改动
- 新增 `Cassette/Utilities/LyricsParser.swift`（LRC/纯文本 → StructuredLyrics）
- 新增 `Cassette/Utilities/LyricsLanguage.swift`（语言码规范化 + 匹配）
- 重写 `LyricsService`：乐观探测（能力仅作诊断）+ legacy 回退 + 缓存 TTL（synced 7d / unsynced 1d / 负缓存 6h）
  + `invalidate()`；能力表为空且 isOpenSubsonic 时强制 `refreshCapabilities()` 一次
- `LyricsViewModel`：二分查找行定位（遇 nil start 降级线性）、`retry()`、接收 title/artist
- `LyricsView`：三个失败态加 "Try again" 按钮
- 新增 `LyricsParserTests` / `LyricsLanguageTests`，补充 Service 与 ViewModel 测试

### 验证方式（重要，见 MEMORY.md）
xcodebuild 在本环境不可用（SwiftPM 要 spawn 沙盒子进程，被拒）。
改用 `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` + `swiftc -typecheck`，
SwiftData 宏用 mock 替身；纯逻辑单独编译成可执行程序跑断言。
二分查找与原线性扫描做了 15 万次随机对比，零差异。

## 第二轮：占位假歌词 + 网易云 JSON 混合格

用户拿网易云下载的真实文件测试（`/Users/even/mine/music/12/`），app 仍显示 "暂无歌词"。

### 根因（新增两类）
6. **下载器占位文件**：网易云下载器在源歌曲没有歌词时写 `[00:00.00]暂无歌词`。
   整库 49 个 lrc 文件里有 14 个是这种假歌词（13%）。app 之前会把它们当合法
   同步歌词渲染，"暂无歌词"四个字直接当成歌词显示。
7. **网易云 yrc 混合格**：真歌词文件前几行是 JSON `{"t":-1000,"c":[{"tx":"作词: "},{"tx":"0"}]}`，
   后面才是标准 LRC。原解析器不认识 JSON，把它们当普通文本渲染成乱码。

### 改动
- `LyricsParser` 新增 `parseNetEaseJSONLine`（处理 `t`/`c`/`tx`，负 `t` 钳为 0）
  + 同时间戳下 LRC 行排在 JSON credits 前面（让标题置首）。
- `LyricsParser.isPlaceholder`（raw 与 structured 两个重载）+ 占位词集合
  （`暂无歌词` / `纯音乐` / `纯音乐，请欣赏` / `此歌曲为没有填词的纯音乐，请欣赏` 等）。
- `LyricsService`：在 `getLyricsBySongId` 之后调 `droppingPlaceholders(list)`，
  在 `legacyFallback` 内部检查 raw 是否占位（占位则 `return nil`）。
- `LyricsParserTests` 增 3 个 suite（NetEaseJSON / Placeholder / 占位结构化条目）。

### 关键经验
- 占位检测**必须**比对整个 line set 而非首行——首行占位但含真歌词要保留。
- JSON 排序的 tie-break 重要：NetEase 用负 `t`（钳 0），标题也是 `[00:00.00]`，
  稳定排序时若不指定 kind rank，"作词: 0" 会跑到标题前面去。
- 同模块编译 SwiftSonic 时 IRGen 会因为 `Codable + same-module retroactive`
  触发 signal 6 崩溃（详见 MEMORY.md）。绕路：先把 SwiftSonic 编译成 dylib
  (`-emit-library`)，再 `-I/-L` 引用。

## 第三轮：全屏歌词自动弹出 + 歌词替代 now-playing 歌名

用户截图反馈（全屏页 + 歌词面板，宋冬野「斑马，斑马」），要两个新功能：
1. 播放 15 秒后自动全屏播放歌词，任意点击恢复封面。
2. 播放时用当前歌词行替代 now-playing 标题，给只显示歌名的车机看。

### 改动
- `NowPlayingServiceProtocol.setLyricTitle(_:)` 新增；`NowPlayingService` 实现
  用 actor-isolated `lyricTitle` 覆盖 `MPMediaItemPropertyTitle`，位置合并分支
  也保留覆盖；live stream 不覆写。
- 新增 `NowPlayingLyricsCoordinator`：0.5s `Timer` + `MainActor.assumeIsolated`，
  按 `PlayerState.position` 找当前行 → 调用 `setLyricTitle`。
  - lyrics 通过 `LyricsService.fetchLyrics(...)` 复用 lyric view 的缓存。
  - 用 `selectBestLanguage(from:)`（`nonisolated`）。
  - 只在 `structured.synced == true` 时启用；二分定位 + `nil start` 降级线性，
    和 `LyricsViewModel` 完全一致的语义。
  - UserDefaults 开关 `cassette.player.lyricsInNowPlaying`（首次默认开启）。
- `AppContainer` 装配 coordinator 并 `start()`。
- `LyricsSettingsSection`（新文件）+ `SettingsView` 嵌入：开关 + 说明文案。
- `FullPlayerView` 加 `@State hasAutoEngagedLyrics` / `isAutoLyricsMode`：
  - 切歌时两个都 reset。
  - `onChange(of: playerState.position)` 触发 `autoEngageLyricsIfNeeded`：
    守卫条件 = `surface == .player` && 非 live && `.playing` &&
    `position >= 15` && `lyricsViewModel.state == .loaded(structured)`
    且 synced + lines 非空 && `!hasAutoEngagedLyrics`。
  - 抽出 `View.lyricsTapToDismiss(isAutoLyricsMode:onDismiss:)` 扩展：
    自动模式用 `contentShape(Rectangle())` + `highPriorityGesture(TapGesture)`
    拦截任意点击；手动模式用 `onTapGesture` 让行点击 seek，空区点击关闭。
  - `dismissLyrics()` 把 `isAutoLyricsMode = false` 但
    `hasAutoEngagedLyrics` 保持 `true`，避免 0.5s 后又被 position tick 重新拉起。
  - iOS `surfaceStack` 和 macOS `playerSurface` ZStack 两个 LyricsView 用法都挂上扩展。

### 关键经验
- `NowPlayingService.setLyricTitle` 最初在 `MainActor.run` 里读 actor-isolated
  状态（`currentSong`/`lyricTitle`），触发 Swift 6 strict concurrency 错误。
  → 必须在 actor 上下文读+写+算出 `newTitle`，把结果捕获为 local
  再 `MainActor.run` 里只动全局 `MPNowPlayingInfoCenter`。
- 0.5s `Timer` 复用 lyric view 的 cadence 比新建更经济。
- 自动模式 vs 手动模式手势区分必须用 `highPriorityGesture`：
  手动模式下「点歌词行 seek」不能被「任意点关闭」抢断。
- 重入守卫必须独立于"当前是否在自动模式"，否则关掉就立刻被下一个 tick 拉回。
- Coordinator 独立于 lyric view 跑，所以后台播放时锁屏 / 车机 / 通知中心
  持续显示当前歌词行（关掉 player view 不影响）。

## 第四轮：全屏歌词不滚动 + 重影修复（LyricsView / LyricsLineView）

用户反馈全屏歌词两个 bug：1) 歌词不跟着歌曲滚动；2) 歌词出现重影。
原因都出在上游 CassetteLab/cassette 原版的 "tiered blur + scale" 设计（本地=上游）。

### 根因
1. **不滚动**：`LazyVStack` 只懒加载靠近视口的行，`scrollTo(id, anchor: .center)`
   对未构建的 index 静默 no-op → 歌词列停住。且没有首次居中的触发：
   视图出现时 `currentLineIndex` 已非 nil，`onChange` 不再触发，列永远贴顶。
2. **重影**：`.blur(radius: 6)`（distance≥3 的行）+ `.scaleEffect(1.05)` 叠加在顶部/
   底部渐隐 mask 上，文字边缘产生光晕式双重影。当前行 scale 变化还会让整列跳动。

### 改动（`Cassette/DesignSystem/Components/Lyrics/`）
- `LyricsView.loadedContent`：`LazyVStack` → `VStack`（所有行都 materialize，
  scrollTo 一定能找到目标）；加 `.onAppear` 首次居中（animated:false）+ `.onChange(of: state)`
  语言切换/重试后重居中；抽 `scrollToCurrent(_:in:animated:)` 复用居中逻辑。
- `LyricsLineView`：去掉 `.blur` 和 `.scaleEffect`，改为「当前行 bold + 其余按距离
  opacity 衰减」(1.0/0.55/0.32/0.18)；字号恒定不随 distance 变 → 行高不变 → 不跳行。
- 更新顶部 doc comment。

### 关键经验
- **SwiftUI scrollTo 必须用非懒加载容器**做歌词视口居中；Lazy 会吞掉对未生成行的 scroll。
- 歌词渐进强调用 **opacity + weight**，不要用 blur/scale——blur 在渐隐 mask 下必然糊成
  重影，scale 造成布局跳动。字号必须恒定。
- `.onChange` 只在「值变化」时触发；首次渲染已就位的状态要用 `.onAppear` 兜底补一次居。

### 验证
- `swiftc -parse` 6 个修改/新增文件全部通过。
- 把 SwiftSonic 编成 dylib（`/tmp/lyrcheck/libSwiftSonic.dylib`），
  用 minimal app-type stubs（`/tmp/coordcheck/AppStubs.swift`）
  做 `swiftc -typecheck -swift-version 6 -I /tmp/lyrcheck -L /tmp/lyrcheck -lSwiftSonic`，
  Coordinator.swift 全字段（`.value`/`.start`/`.synced`/`.line`/`.offset`/
  `selectBestLanguage(from:)`/`fetchLyrics(...)`）对得上真实 API，零错误。
  完整流程已沉淀为 skill `swift-dylib-typecheck`。

## 歌词重影/错位根因：CR-only `.lrc` 行尾（已修）
- 现象：iOS 全屏歌词前几行正常，之后整片歌词互相叠压、错位（同屏多句叠写）。
- 根因（用真实 `LyricsParser` + SwiftSonic dylib 复现证实）：**`.lrc` 用裸 `\r` 做行分隔符**
  （旧 Mac / 部分下载器）。`parseTimedLines`/`parsePlainLines` 只按 `\n` 切分 →
  整首歌被当成**一行**，`value` 是全部歌词用 `\r` 连接、且混着内联 `[00:xx]` 时间戳，
  例如 `lineCount=1`、`value="斑马斑马 你不要睡着啦\r[00:15.67]再给我看看…"`。
  `Text` 渲染带 `\r` 的字符串时后缀会**回行首叠写** → 重影；且这一行是唯一"当前行" → 滚动/高亮全乱。
- 修法（`LyricsParser.swift`）：
  1. 新增 `normalized(_:)`：`\r\n`->`\n`、`\r`->`\n`，在 `parseTimedLines`/`parsePlainLines`/
     `parseMetadata`/`placeholderCandidates` 内部先归一化再切分。
  2. 新增 `cleanValue(_:)`：剔除残留 `\r`、`\n`->空格、trim 行值；`netEaseJSONLineText` 也用。
  3. 复现对比：修复前 `lineCount=1`（巨行含 `\r`）；修复后 `lineCount=6`、每行独立时间戳、值干净。
- 视图层兜底（`LyricsView.swift`）：渲染每行时 `line.value.replacingOccurrences(of:"\r", with:"\n")`，
  防止任何来源（含服务器 `getLyricsBySongId` 直接返回的行值）里的 `\r` 造成覆盖——`\r` 转纵向换行，
  宁可向下排、绝不叠写。
- 回归用例：`LyricsParserTests.swift` 新增 `splitsCROnlyLineEndings` + `normalisesStrayCarriageReturnInValue`。
- 验证：`swiftc -parse` 三个文件全 clean；harness 用真 SwiftSonic dylib 跑 7 组样本全部符合预期。
- 教训：解析外部歌词文本，**切分前必须归一化行尾**（CRLF/CR/LF），否则任何纯 `\r` 文件都会塌成一行；
  `\r` 会让 `Text` 叠写（与 `\n` 换行是两回事）。
